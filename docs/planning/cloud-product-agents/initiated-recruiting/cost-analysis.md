## What is charged incrementally

The model counts Recruiting specialist tokens, short-lived Cloud Run worker/browser time, marginal Firestore/Storage/logging/secret use, incremental Linux CI and optional search. Existing shared GCP schedules remain the same, so Recruiting scheduler jobs are zero. It assumes no extra macOS runner time, second coordinator or dashboard hosting instance, commercial analytics subscription, bulk email service, always-on worker or separate agent SaaS. GA4 aggregate queries, artifact operations, registry and backup costs are **allowances** pending invoice/usage measurement, not quoted vendor fees. One released CI run is counted once: reusing an existing result has zero incremental runner minutes, while an additional targeted run consumes the modeled Linux allowance.

Vendor rate assumptions were checked 2026-09-28 against [OpenAI API pricing](https://developers.openai.com/api/docs/pricing), [Claude API pricing](https://platform.claude.com/docs/en/about-claude/pricing), [Cloud Run pricing](https://cloud.google.com/run/pricing), and [GitHub Actions runner pricing](https://docs.github.com/en/billing/reference/actions-runner-pricing); the remaining infrastructure links and regional assumptions are in the [shared cost analysis](../cost-analysis.md). Model availability, account entitlements, region, rate changes, billed image/reasoning tokens and actual GA4 query behavior must be verified at implementation. No free tier, cached-token, batch, subscription or negotiated discount is deducted. The 30% retry/context multiplier applies to modeled tokens and worker/browser runtime once; the additional 25% is unspent planning headroom rather than an expected invoice.

Balanced workload means about 300 triage events, 24 PM reviews, 12 design reviews, 60 engineering reviews, four deep investigations, eight repair attempts, 24 follow-ups, 120 lightweight browser probes and 900 additional Linux CI minutes in a 30-day month. Those volumes require actual issues/releases; the system should never create synthetic defects to meet a cost or acceptance target. About $126 of the balanced $173 is model inference, $6 is Cloud Run workers/browser/control, $5 is added Linux CI, and $30 is the two ancillary allowances. Rounding and the other small state/storage/logging items appear in the generated breakdown. At 2× assumed tokens, balanced modeled cash rises to $299/month; at 5×, $679/month. Repeated large-context repair work is the main cash sensitivity.

## Build, operating time and value

Recruiting stories total **82–148 founder-active build hours**, or **98–178 hours** with one 20% schedule reserve. At 20 focused hours/week, that is 4.9–8.9 equivalent build weeks, plus fixed shadow and comparison observation windows; the [six-sprint plan](sprint-plan.md) spans 12 calendar weeks if gates and access cooperate. A $50–150 **incremental** setup/test cash allowance is separate from recurring usage and existing subscriptions. The generic 16–32-hour second-product placeholder in the original shared plan is superseded by these detailed journey/security/evaluation stories and must not be added again.

Monthly founder operating time includes digest/finding oversight, platform maintenance attributable to Recruiting and 0.5–1.0 active hours reviewing each repair attempt, including rejected ones. It excludes coding work for unsolved defects, customer research and existing human release approval work unless the assisted workflow actually changes that time. Do not count both a repaired defect as coordination saved and new throughput if it had no comparable current-workflow task.

For the balanced scenario, midpoint operating time is 13 hours/month and midpoint reserved build time is 138 hours. If comparable current coordination is 12 hours/month, the modeled service costs an extra hour of founder time and has no time payback. At 25 hours/month, the illustrative net saving is 12 hours/month and build-time payback is about 11.5 months; at 40 hours/month it is 27 hours/month and about 5.1 months. The $216 monthly cash envelope equates to roughly $18 or $8 per saved hour in those latter cases. These are sensitivity examples, not a measured ROI or salary value. The first two weeks must log the actual current AI-assisted baseline by task class before deciding whether the service is worth building further.

Twelve operating months **after** integration plus one setup allowance yield $2,126–2,226 modeled incremental balanced cash, or $2,645–2,745 with operating reserve. Founder operating time is 108–204 hours/year in addition to the one-time build. This is not a first-calendar-year cash forecast because the 12-month operating period starts after implementation.

## Cost and benefit measurement

Meter provider tokens by model and work order, Cloud Run seconds, browser minutes, extra CI minutes, storage/egress, GA4 query cost if any, retries and aborted runs. Show cost per confirmed nonduplicate finding, cost per accepted repair, and cash per net founder hour saved. Measure current-workflow and agent-assisted tasks with the same eligibility and quality rules. Report the 14-day shadow window separately from the four-week live comparison: shadow proves run quality, while comparable allocation estimates time saved. Missing live task volume means an inconclusive economic result, even if synthetic tests pass.

Reforecast after R1 access/baseline inventory, the first shadow week and each comparison sprint. Pause discretionary deep reviews when metered tokens exceed 2× assumptions or the reserved task budget; keep access/security checks active. A new paid analytics service, daily full E2E suite, broader repair permissions or mobile device-farm work requires a new estimate and explicit category policy before inclusion.
