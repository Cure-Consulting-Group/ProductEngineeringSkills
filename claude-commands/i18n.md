# Internationalization & Localization

**Outcome:** user-facing text externalized with Cure key naming, plurals and formatting delegated to
CLDR-aware platform APIs, RTL correct where in scope, and CI that fails on missing or broken
translations. Done when the Step 1 deliverable exists and a pseudolocale run shows no hard-coded or
truncated strings on the touched screens. Match length to the need; no filler sections.

## Pre-Processing (Auto-Context)

Context (pre-filled in Claude Code; in other runtimes run these commands first):

- i18n libraries: !`grep -hoE '"(next-intl|i18next|react-intl|@formatjs/[a-z-]+|next)": "[^"]+"' package.json 2>/dev/null | head -6 || echo "(no package.json)"`
- String files: !`find . \( -name "strings.xml" -o -name "*.xcstrings" -o -name "Localizable.strings" -o -path "*/messages/*.json" \) -not -path "*/node_modules/*" -not -path "*/build/*" 2>/dev/null | head -10`

## Step 1: Classify

| Request | Deliverable |
|---|---|
| Greenfield setup | Platform config + source string files + lint rule + CI checks |
| Add a locale | Locale files, routing/config entry, formatting and plural review for that locale |
| RTL support | Per-screen mirroring changes + bidi handling + RTL screenshot tests |
| Translation workflow | Export/import pipeline + CI validation |
| i18n audit | Findings (hard-coded strings, concatenation, manual formatting, plural bugs), each with file:line and severity; report everything found |
| Formatting | Formatter setup for dates, numbers, currency |

## Step 2: Gather Context

Platforms; target locales (with regions, e.g. `es-MX`); any RTL locale (Arabic, Hebrew, Farsi, Urdu);
greenfield vs existing hard-coded strings; string volume; translation provider (Cure default:
Lokalise, Phrase, or Crowdin — whichever the client already pays for); server-driven strings.

## Step 3: Cure Conventions

- Keys are `feature.screen.element` (`auth.login.submit_button`). Android resource names can't
  contain dots — use `auth_login_submit_button` there and keep the same hierarchy.
- Never concatenate translated fragments; use named parameters (`{name}`) or positional specifiers
  (`%1$s`) so translators can reorder.
- Plurals and gender/select go through ICU MessageFormat (web), `<plurals>` (Android), or String
  Catalog variants (iOS) — never `if (count == 1)`.
- Dates, numbers, currency: platform formatters with an explicit locale and an explicit ISO currency
  code. Store phone numbers in E.164 and format with libphonenumber.
- Server-driven copy (Remote Config, CMS) always has a bundled fallback; missing translations fall
  back to the default locale, never to a raw key.

## Step 4: Platform Implementation

### Android
- Files: `res/values/strings.xml`, `res/values-es/`, `res/values-b+es+419/` (BCP-47 form for
  script/region), `res/xml/locales_config.xml` + `android:localeConfig` for the per-app language
  picker (Android 13+).
- Compose: `stringResource()`, `pluralStringResource(R.plurals.x, count, count)`. ViewModels emit
  `@StringRes` IDs, not resolved text.
- Locale switch: `AppCompatDelegate.setApplicationLocales(LocaleListCompat.forLanguageTags("es-MX"))`.
  Build `java.util.Locale` with `Locale.forLanguageTag("es-MX")`; the `Locale(String, String)`
  constructors are deprecated since JDK 19.
- **Plural gotcha:** `quantity="zero"` is ignored in English (and most locales) — CLDR has no
  grammatical zero there, so `0` resolves to `other`. For a "No orders" empty state, branch on
  `count == 0` to a separate string, then use `<plurals>` for the rest. Provide every category the
  target locale needs (Arabic: zero, one, two, few, many, other).
- Lint: Android Lint `HardcodedText` + a detekt/Compose rule for literals in `Text()`.

### iOS
- String Catalog `Localizable.xcstrings` (Xcode 15+); plural and device variants are edited in the
  catalog. `Text("auth.login.title")` looks up keys; outside views use `String(localized:)`.
- Formatting: `Date.FormatStyle`, `.formatted(.currency(code:))` with the user's locale.
- Previews: `.environment(\.locale, Locale(identifier: "ar"))` and
  `.environment(\.layoutDirection, .rightToLeft)`.

### Web (Next.js + next-intl 4.x)
Cure's one web stack is next-intl (4.14 current, verified 2026-09-23) — not i18next/react-intl in
new Next.js work.
```
messages/en.json, messages/ar.json   ICU messages, nested by feature
i18n/routing.ts                      defineRouting({ locales, defaultLocale })
i18n/request.ts                      getRequestConfig → loads messages for the locale
proxy.ts                             locale negotiation (Next 16 renamed middleware.ts → proxy.ts)
app/[locale]/layout.tsx              <html lang={locale} dir={dir}>, setRequestLocale
```
```ts
// proxy.ts
import createMiddleware from 'next-intl/middleware';
import {routing} from './i18n/routing';
export default createMiddleware(routing);
export const config = {matcher: '/((?!api|trpc|_next|_vercel|.*\\..*).*)'};
```
Server components: `const t = await getTranslations('auth.login')`; client: `useTranslations`.
Formatting: `useFormatter()` / `Intl.*` — never moment.js. On Next ≤15 the same file is
`middleware.ts`. Lint untranslated JSX with an i18n ESLint rule (flat config).

## Step 5: RTL

- Direction is per locale: set `dir="rtl"` on `<html>` for RTL locales and `dir="ltr"` otherwise,
  computed from the locale in the layout. `dir="auto"` on `<html>` guesses from the first strong
  character of the content and flips layouts unpredictably; reserve `dir="auto"` for individual
  user-generated text elements.
- CSS logical properties (`margin-inline-start`, `inset-inline-end`); Android `start`/`end` with
  `supportsRtl="true"`; SwiftUI `.leading`/`.trailing`.
- Mirror directional icons (back, forward, progress); don't mirror clocks, checkmarks, media
  controls, or logos.
- Isolate embedded opposite-direction runs (brand names, phone numbers, URLs, code) with `<bdi>` on
  web or Unicode isolates `U+2066…U+2069`.

## Step 6: Testing and CI

- Pseudolocales: Android `en-XA` (accents + ~40% expansion) and `ar-XB` (RTL); iOS scheme "App
  Language → Double-Length Pseudolanguage" / right-to-left pseudolanguage; web generated
  pseudolocale JSON. Run UI tests under them in CI.
- Screenshot baselines: default locale + one RTL locale + the longest locale (often German).
  Android Roborazzi/Paparazzi, iOS snapshot tests, Playwright with `locale` set.
- CI checks: every source key exists in every shipped locale (new locales under translation may be
  allow-listed); format-specifier and ICU placeholder parity; ICU syntax parses; no empty values.
- Manual pass: plurals in a complex-plural locale, localized accessibility labels, push and deep
  links in the right locale, language switch without restart.

## Code/Artifact Generation

Applies when Step 1 calls for setup, a new locale, RTL, or a workflow; an audit or question gets
findings or an answer, not files. Extend the existing i18n setup found above rather than adding a
second library. Typical files: lint rule config, source string files, platform config (the next-intl
files above for web), `scripts/check-translations.*`, pseudolocale generation.
